# 验证执行（run-verification）

## 描述
TSP 采用分层验证矩阵（`CONTRIBUTING.md` §9）：后端定向 pytest + Ruff、前端 `pnpm build`、提交前 `git diff --check`。本技能让验证可复现、结果如实汇报。

## 使用场景
- 开发/复审完成后需要执行适用验证。
- 用户说"跑相关测试/前端构建/检查改动"。
- 需要判断"这次改动该跑哪些测试"。

## 指令

1. **识别改动范围**：查看 `git status --short --branch` 与改动文件，按 `CONTRIBUTING.md` §9 表格归类：
   - 后端纯函数/规则/Bug 修复 → 对应定向 pytest（含复现与边界用例）
   - API 契约 → service 测试 + API 测试（成功/无数据/错误）
   - 数据源或插件 → provider 契约/缺能力/空数据/字段单位标准化测试
   - 指标/复权/换手/涨跌停 → 固定样本数值断言测试
   - 策略/监控 → 参数变更/缓存失效/资产切换/重启并发相关测试
   - 回测 → 信号日与成交日/T+1/费用滑点/数据缺口测试
   - 缓存或性能 → 命中失效/并发快照测试
   - 前端 → `pnpm build`；前后端契约同变 → 后端测试 + 前端构建
   - 文件/Docker/跨平台 → 失败路径检查

2. **执行后端验证**（在 `backend/` 目录）：
   ```bash
   uv run pytest tests/<受影响测试文件> -q
   uv run ruff check app/<改动模块>.py tests/<改动测试>.py
   ```
   - 至少运行受影响模块的测试，不只运行新加的单个测试。
   - 新增/改动文件不得引入 Ruff 告警。
   - 依赖实时数据源、外部网络或付费档位的用例（如 `*_live`、探测类）如环境不满足，明确标注跳过原因，不硬跑。

3. **执行前端验证**（在 `frontend/` 目录，任何 TS/组件/样式/API 类型改动必须）：
   ```bash
   pnpm build
   ```

4. **提交前检查**（仓库根目录）：
   ```bash
   git diff --check
   ```

5. **汇报结果**（禁止虚构；未运行的验证必须标注）：
   ```text
   改动范围：...
   验证命令与实际结果：命令 / 通过或失败 / 失败摘要
   未执行项与原因：...
   剩余风险：...
   ```

## 注意
- 不擅自运行全量测试套件或耗时优化，除非改动影响面大且用户确认。
- 运行命令前先确认工作目录（backend/frontend 根），善用仓库现有 `uv` / `pnpm`，不引入新的包管理器。
- 验证失败时给出失败用例名与断言信息，不掩盖、不重试掩盖问题。
